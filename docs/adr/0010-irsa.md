# ADR-0010: IAM Roles for Service Accounts (IRSA) for pod AWS access

- **Status:** Accepted
- **Deciders:** Platform owner

## Context
Pods need AWS permissions (S3, Secrets Manager) without static keys, and without handing every pod the node's permissions.

## Decision
Each controller or workload that talks to AWS has its own IAM role whose trust policy pins the cluster OIDC `sub` claim to one `namespace:serviceaccount`. The role ARN is an annotation on the ServiceAccount. The node role carries only kubelet/CNI/ECR-pull permissions.

## Consequences
Per-workload least privilege and no credentials to leak or rotate; a compromised pod elsewhere cannot assume the role. Costs: one role per workload and per environment, and trust policies tie roles to a specific cluster's OIDC provider. EKS Pod Identity (already enabled as an add-on) is simpler to manage and is the likely future default; IRSA was kept because it is still what most clusters and interviewers use.

## Alternatives considered
EKS Pod Identity (simpler, no OIDC trust per cluster); node instance role (every pod shares it, rejected); static keys (rejected).
